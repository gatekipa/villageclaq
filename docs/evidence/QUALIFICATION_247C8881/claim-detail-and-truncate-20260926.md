# Claim-detail and ordinary TRUNCATE qualification

Owner: Daybreak Blue. Target: the dedicated repair branch, after the local Relief checkpoint `59459fe304dd9e593adb8088f90c3c9105405130`. No production write, migration, merge or deployment occurred.

## Read-only production catalog finding

Supabase project `llbnliixczcqfftxpsmb` was queried **only for schema and privilege metadata**. `authenticated` has effective `TRUNCATE` on **90 public base tables** owned by `postgres`; `anon` also holds explicit `TRUNCATE` on many of them. `authenticated` also has `TRUNCATE` and schema `USAGE` on `storage.objects`, `storage.buckets` and `storage.buckets_analytics`, granted by their owner `supabase_storage_admin`. `storage.objects` and `storage.buckets_analytics` have no incoming foreign keys. The connected `postgres` role is **not** a member of `supabase_storage_admin` and cannot change that role's default privileges. These are effective grants; RLS cannot authorize or filter `TRUNCATE` ([PostgreSQL REVOKE/privilege documentation](https://www.postgresql.org/docs/17/sql-revoke.html)). No production table contents, credentials or secrets were read.

## Before/after local behavior

- On the prior S0/M2-compatible local catalog `villageclaq_upgrade_replay30`, `authenticated` retained `TRUNCATE` on 81 public tables after the narrower Relief grant repair. Inside a rollback transaction, a fictional FAQ row was inserted, `SET ROLE authenticated; TRUNCATE public.faqs` **succeeded**, and the row count became 0. The transaction rolled back. This demonstrates an executable database-role privilege that bypasses row policies. A normal browser/API path to issue this command has **not** been demonstrated; the operation was not performed on production.
- On the pre-repair local catalog, `scripts/test-relief-claim-detail-scope.sql -v expected_suspended_visible=true` showed both a **suspended admin** and unrelated **platform support** could read a fictional claimant's private detail through old OR-combined SELECT policies. The claimant and active reviewer also saw it; an unrelated group did not.
- `00146_relief_claim_detail_scope.sql` removes those broad SELECT policies and requires the claimant identity or current operational `relief.manage` permission. The same probe with `expected_suspended_visible=false` denies suspended admin and platform support, preserves claimant and active reviewer reads, preserves an active reviewer's update, and denies an unrelated group. No claim or account data leave the transaction.
- `00147_revoke_ordinary_truncate.sql` revokes `TRUNCATE` on existing public tables from `PUBLIC`, `anon`, and `authenticated`, then removes it from the `postgres` public-table default ACL for future migration-owned tables. `scripts/test-no-ordinary-truncate.sql` verifies zero effective public-table grants to those roles, no such postgres default grant, and direct `authenticated TRUNCATE public.faqs` permission denial. The local diagnostic passed.

A fresh S0/M2-compatible PostgreSQL 17.11 catalog `villageclaq_upgrade_replay33` applied all 34 repository migrations `001170`–`00147` in order with `ON_ERROR_STOP=1`. Both focused probes passed there. Direct SQL remains a **diagnostic**, not a Supabase migration-history rehearsal. The existing F24 fixture remains limited to its stated scope.
