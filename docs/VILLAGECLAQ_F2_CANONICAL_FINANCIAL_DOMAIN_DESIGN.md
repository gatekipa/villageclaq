## 1. Purpose

VillageClaq Financials will become the authoritative financial operating system for community organizations.

An authorized officer records a legitimate **Financial Event** once. VillageClaq then maintains the affected balances, member positions, reports, exports, standing dependencies, audit evidence, and financial-health views from that single write.

Operating promise (unchanged from the PRD):

> **Record the financial event once. VillageClaq maintains the truth everywhere else.**

Report doctrine (unchanged from the PRD):

> **A report is a view of financial truth. A report is not financial truth.**

F2 freezes the objects, ledger semantics, cash-basis rule, event taxonomy, subledger classifications, idempotency, accounts/funds/categories, multi-currency, dates, status, correction, opening position, report projections, standing consumption, permissions, security, and the bounded F3 ticket cut. F3 may implement only the minimum scope in §24.

## 2. Alignment with PRD layers A–E

This design does not replace the PRD architecture. It names the canonical objects that realize each layer.

| PRD layer | Business question | Canonical realization (F2 freeze) |
|---|---|---|
| **A — Organization financial ledger** | What happened to the organization's money? | **Financial Event** is the user-understood write unit. **Postings** are the balanced accounting lines generated by that event. |
| **B — Financial accounts** | Where is the organization's money? | **Account** = custody. Balance is derived from postings. |
| **C — Financial dimensions** | Why did this happen and what is it for? | **Fund** (purpose/restriction), **Category** (income/expense class), optional **project/program**, optional **member**, optional **contribution type**, plus source link. |
| **D — Specialized subledgers** | What does this module mean for members/programs? | Dues, fines, loans, projects, relief, Njangi retain their own rules. Each economic effect emits **at most one** canonical Financial Event. |
| **E — Reporting projections** | What should officers see? | All organization reports project from canonical postings (+ dimensions). Contribution ledger / member statement may join source links to the dues subledger. |

No layer may become a second money truth.

## 3. Object model

Users never see a separate Transaction object distinct from Financial Event. **Financial Event is the unit.**

### 3.1 Canonical objects

| Object | User-visible? | Meaning | Authority |
|---|---|---|---|
| **Financial Event** | Yes | The user-understood business event. Canonical write unit for the organization ledger. | One event is the single recorded fact officers and auditors talk about. |
| **Posting** | No | Balanced accounting lines generated by an event. Backend only. | Users never see debit/credit language. |
| **Account** | Yes | Custody / where money is held. | Bank, cash, mobile money, wallet, other. |
| **Fund** | Yes | Purpose / restriction. | Unrestricted/general, emergency, project, relief, other. Custody ≠ purpose. |
| **Category** | Yes | Income/expense classification. | Separate from accounts, funds, projects, and contribution types. |
| **Source link** | Audit/drilldown | Pointer to the originating subledger/module. | `source_type` + `source_id`, plus `request_id` / `correlation_id`. |

Do **not** introduce a separate user-facing Transaction object unless a later gate proves it is required. F3 must not add one.

### 3.2 Dimensions on an event

Every Financial Event is scoped to the organization ledger and may carry:

| Dimension | Required? | Notes |
|---|---|---|
| Group / branch | Required | Ledger scope. Matches PRD: `group` is the authoritative financial ledger scope. |
| Ledger epoch | Required (inherited) | Group has one active currency per dated ledger epoch. |
| Currency | Required | Inherited from account + epoch. One event = one currency. |
| Account(s) | Required for money movement | Custody involved. Transfers use two accounts of the same currency. |
| Fund | Required on money events | Defaultable to unrestricted/general. |
| Category | Required on Money In / Money Out | Not required on Transfer. |
| Member | Optional | Present when the event is about a person (collection, reimbursement, credit application). |
| Project / program | Optional | Dimension first. Optional dedicated project fund later if restriction requires it. |
| Contribution type | Optional | Subledger dimension; does not replace Category. |
| Source link | Required when originated by a module | Manual events may have `source_type = manual`. |

### 3.3 Conceptual identity (not a migration)

F3 will persist these as group-scoped rows. This section is a design contract, not DDL.

**Financial Event (conceptual fields)**

- `id`
- `group_id`
- `ledger_epoch_id` (or equivalent epoch binding)
- `currency`
- `ux_class` — `MONEY_IN` \| `MONEY_OUT` \| `TRANSFER` \| `OPENING_ADJUSTMENT`
- `category_id` (null on Transfer)
- `fund_id` (default unrestricted/general)
- `account_id` (primary custody; Transfer also has `destination_account_id`)
- `amount` (unsigned magnitude in native currency; direction comes from `ux_class` + postings)
- `member_id` (optional)
- `project_id` (optional)
- `contribution_type_id` (optional)
- `source_type`, `source_id`
- `request_id` / `correlation_id`
- `occurred_at`
- `posted_at`
- `created_at`
- `status` — `DRAFT` \| `POSTED` \| `CORRECTED` \| `REVERSED`
- `corrected_at`, `reversal_of_event_id`, `replacement_event_id` (when applicable)
- actor, reason, evidence refs

**Posting (conceptual fields)**

- `id`
- `event_id`
- `group_id`
- `account_id` (custody line; may be a system/control account for income, expense, receivable, liability — see §4)
- `fund_id`
- `amount_signed` or explicit `direction` + `amount` (backend only)
- `currency`
- `occurred_at` (copied from event; reports use this)

Posting language is internal. UX copy is Money In / Money Out / Transfer / Opening-Adjustment only.

## 4. Ledger model

**Frozen choice: B — lightweight balanced posting journal behind simple UX.**

- Financial Events create balanced postings **per currency**, within the group/org ledger scope.
- Users see **Money In / Money Out / Transfer / Opening-Adjustment**.
- Users never see debit, credit, journal, chart of accounts, or trial-balance jargon.
- This is **not** QuickBooks or NetSuite.
- Do not build an enterprise chart-of-accounts builder (PRD non-goal).

### 4.1 Balance rule

For each Financial Event, generated postings must balance to zero in that event's single currency inside that group ledger.

Illustrative backend intent (never shown as debit/credit to users):

| UX | Example | Backend posting intent |
|---|---|---|
| Money Out | $50 venue / fuel from Operating Bank | Expense dimension +50; Operating Bank −50 |
| Money In | $100 confirmed contribution to Bank | Bank +100; income/contribution-receipt effect +100 |
| Transfer | $500 Bank → Cash | Bank −500; Cash +500; **no income or expense** |
| Opening | Opening cash $20,000 | Account +20,000; opening-equity/opening-position counterpart; **not** a payment |

Internal control accounts (income, expense, opening position, receivable, liability) exist so postings can balance. They are not user-facing Account kinds. User-facing Accounts are custody only (§10).

### 4.2 What the journal is not

- Not accrual-basis organization books.
- Not a full double-entry teaching surface.
- Not a second write path beside subledgers.
- Not an FX engine.

## 5. Cash vs accrual

**Frozen choice: A — cash-basis Statement of Activity + separate receivable/dues subledger.**

| Rule | Freeze |
|---|---|
| Creating a dues obligation | Does **not** create organization income. |
| Confirmed collection | Creates organization income **and** cash/account movement. Obligation/AR lives in the dues subledger. |
| Statement of Activity | Reads **ledger postings** only. |
| Member statements / AR / aging / who-hasn't-paid | Read the **dues subledger** (and source links). |
| Double counting | Forbidden. The same economic cash collection must not appear as income in SoA from both a subledger total and a ledger posting. |

### 5.1 Avoid-double-count contract

- SoA income/expense = posted ledger lines classified as income or expense.
- Transfers never enter SoA.
- Loan principal never enters SoA as income or expense.
- Opening arrears are subledger/opening position, not period income and not fake payments.
- Contribution collection is recognized **once**, when confirmed, via the canonical event.

## 6. Event taxonomy

### 6.1 UX top-level classes (sparse)

Keep types sparse. Use category / fund / project dimensions instead of dozens of event types.

| UX class | Meaning | SoA effect | Cash/account effect |
|---|---|---|---|
| **MONEY IN** | Organization received money | Income (except when classification says otherwise — see §7 loan principal) | Increase custody account |
| **MONEY OUT** | Organization paid money | Expense (except when classification says otherwise — see §7 loan disbursement) | Decrease custody account |
| **TRANSFER** | Internal movement between organization-owned accounts | **Never** income or expense | Asset ↔ asset only |
| **OPENING / ADJUSTMENT** | Opening position, correction counterpart, authorized non-cash adjustment | Not ordinary period activity; see §16–§17 | As specified by the opening/adjustment postings |

### 6.2 Sparse subtypes via dimensions, not new classes

Donation, grant, sponsorship, fundraising, project income, fine collected, interest, other income are **categories** (and optional fund/project), not new UX classes.

Operating expense, reimbursement, project expense, relief payout, refund, fee, approved purchase are **categories** (and optional fund/project), not new UX classes.

Loan disbursement and loan principal repayment use Money Out / Money In **UX** with **non-operating economic classification** (§7). The UX class stays sparse; reports must honor classification, not the UX label alone.

F3 may store a backend `economic_class` on the event or infer it from category + source_type. Either is acceptable if projections stay deterministic. Do not explode UX types.

## 7. Subledger economic classifications (frozen)

These classifications are frozen. F4/F5 implementations must emit events that produce exactly these economic effects. They must not invent a second SoA meaning.

| Subledger business effect | Organization ledger effect | Not allowed |
|---|---|---|
| **Contribution confirmed collection** | Income + asset (cash/account) increase | Treating obligation creation as income; counting collection twice |
| **Dues remaining / AR** | Subledger AR only | SoA income |
| **Fine assessment** | Non-cash receivable / subledger | Organization income at assessment |
| **Fine payment** | Income (or fine-income category) + cash | Ignoring cash; posting income at assessment and again at payment |
| **Loan disbursement** | Asset reclass / receivable increase + cash decrease | Operating expense |
| **Loan principal repayment** | Cash increase + receivable decrease | Income |
| **Loan interest payment** | Income + cash | Treating interest as principal |
| **Relief contribution** | Income (or restricted fund income) + cash | Unrestricted income if the fund is restricted |
| **Relief payout** | Expense (or benefit expense) + cash | Omitting org-ledger expense while paying cash |
| **Relief remittance** | As already designed for remittance, without double counting | Posting the same cash as both income and remittance income |
| **Project contribution** | Income (often restricted / project fund) + cash | Treating it as unrestricted operating income when restricted |
| **Project expense** | Expense + cash | Hiding it from org SoA |
| **Njangi contribution / savings** | Liability to members (or member-held savings) + cash | Association unrestricted income |
| **Njangi payout** | Liability decrease + cash | Expense (unless a true fee/interest component is separately classified) |
| **Reimbursement** | Expense (or reduce prior receivable) + cash | Fake contribution; double expense |
| **Member credit** | Liability / credit subledger | Invented income |
| **Member credit application** | Reduces AR or applies as payment attribution | Creating income a second time |
| **Internal transfer** | Asset ↔ asset only | Income or expense |

Remittance, credits, and allocations must preserve the invariant in §8: one business effect, one canonical event, no double posting.

## 8. Subledger → ledger invariant

**ONE subledger business effect → AT MOST ONE canonical Financial Event → deterministic Postings → all organization reports derive from those postings.**

| Rule | Freeze |
|---|---|
| Cardinality | One confirmed economic effect creates at most one Financial Event. |
| Determinism | The same source + effect always yields the same posting set. |
| Report source | Org reports (SoA, Cashbook, Cash Movement, account balances, fund reports) read postings. |
| Subledger remains specialized | Obligation allocation, arrears, credits, standing inputs, loan schedules, Njangi rotations stay in the module. |
| Double posting | Prevented by source idempotency (§9). |
| Preferred integration style | **A: subledger generates canonical events.** Do not rewrite modules as ledger-first. |

A module may decide that a business action has **no** organization-ledger effect (example: creating a dues obligation). That is zero events, which satisfies “at most one.”

A module must not write organization cash/income/expense totals by any path other than the canonical event.

## 9. Idempotency

Retries, crons, webhooks, and client double-submits must not double-post.

| Mechanism | Freeze |
|---|---|
| Source uniqueness | Unique `(group_id, source_type, source_id)` or equivalent. |
| Client retries | `request_id` (or equivalent idempotency key) on the posting command. |
| Repeat delivery | Second insert of the same source key returns the existing event; it does not create a second event. |
| Correction | A reversal/replacement is a **new** event with its own id, linked to the original. It does not reuse the original `source_id` as a second primary post. |
| Manual events | Use `source_type = manual` and a unique `source_id` or `request_id` so retries still collide safely. |

F3 posting command must enforce this at the authoritative server boundary, not only in the UI.

## 10. Accounts

**Account = custody. Where money is held.**

| Decision | Freeze |
|---|---|
| Kinds | `bank`, `cash`, `mobile_money`, `wallet`, `other` |
| Currency | **Single-currency per account** |
| Balance | **Derived from postings.** No manually editable authoritative totals. |
| Scope | Group-scoped (branch ledger). |
| Opening | Via **Opening Position** events only. |
| Lifecycle | `active` → `inactive` → `closed` |
| Currency after open | **Immutable.** To change currency: close the account and open a new one. |
| Epoch | Account belongs to the group's ledger epoch / currency rules. |

### 10.1 What officers cannot do

- Type over a balance field and make that the truth.
- Mix currencies in one account.
- Transfer across currencies in F3.
- Use an account as a category, fund, or project.

### 10.2 Derived balance

For an account in its native currency:

`closing = opening_via_opening_events + money_in − money_out ± transfers`

Opening is itself posting-backed. There is no side table of authoritative running totals.

## 11. Funds

**Custody ≠ purpose.**

One bank account may hold money conceptually reserved for General, Relief, Convention, Scholarship, or other funds.

| Decision | Freeze |
|---|---|
| Default fund | Unrestricted / general. Every group has one. |
| Money events | **Mandatory fund**, defaultable to unrestricted/general. |
| Scope | Org / group. |
| Split across funds on one event | Allowed later if needed. **F3 may start one-fund-per-event.** |
| Projects | **Simplest freeze:** project is a **dimension**. Optional dedicated project fund when restriction requires a separate purpose bucket. Do not require both for F3. |

Funds are not Accounts. Funds are not Categories. Funds are not contribution types.

## 12. Categories

| Decision | Freeze |
|---|---|
| Shape | **Flat list first.** No deep hierarchy in F3. |
| Provenance | System defaults + org-custom. |
| Lifecycle | Archiveable (not destructively deleted while referenced). |
| Separation | Separate from accounts, funds, projects, and contribution types. |

System defaults should cover the sparse taxonomy in the PRD (contributions, donations, grants, fundraising, project income, other income, operations, relief, projects, reimbursements, fees, other) without becoming a full ERP chart of accounts.

A contribution **type** (monthly dues, levy, special assessment) is a subledger concept. It may be a dimension on a collection event. It is not a Category replacement.

## 13. Multi-currency

**Preserve F0. Do not reopen.**

| Rule | Freeze |
|---|---|
| Native ledger epoch | Each group has one active currency per dated ledger epoch. Historical currency is immutable. |
| No silent FX | Never auto-convert, auto-relabel, auto-reassign, or silently infer a branch. |
| No incompatible netting | Monetary values in incompatible currencies are never summed or netted. |
| Parent / HQ | Currency **buckets** only (USD bucket, XAF bucket, …). |
| One event | One currency. |
| Accounts | Single-currency. |
| F3 transfers | **Same-currency only.** |
| Cross-currency transfer | **DEFERRED.** No automatic FX. |

A later converted report, if ever approved, must preserve native amount, rate, rate date, source, and reporting currency. That is not F3.

F0 internal test-tenant classification is a **migration gate only**. It is **not** a runtime financial-integrity bypass (§21).

## 14. Dates

| Field | Lives on | Drives |
|---|---|---|
| **`occurred_at` / transaction date** | Financial Event (copied onto postings) | Statement of Activity, Cashbook, Cash Movement, period reports |
| **`posted_at`** | Financial Event | When the event became `POSTED` (audit) |
| **`created_at`** | System row | Engineering / insert time |
| **`due_date`** | **Subledger only** | Obligations, AR aging — never org SoA period |
| **`corrected_at`** | Correction linkage | Correction/reversal audit |

**Period field contract (frozen):** activity and cash reports share `occurred_at`. Reports must not place the same event in inconsistent periods by mixing `created_at` or `posted_at` into activity totals.

Shared period selectors remain those in the PRD: this month, last month, quarter, year, custom range; optional fiscal year later.

Opening Position dates must not make inherited balances appear as if they became due, earned, or spent in the first VillageClaq reporting period (§17).

## 15. Status / lifecycle

**Frozen lifecycle:**

`DRAFT` (optional, manual only) → `POSTED` → `CORRECTED` / `REVERSED`

| Decision | Freeze |
|---|---|
| Posted history | Append-only **in meaning**. No destructive edit/delete of `POSTED`. |
| Auto subledger events | Post **directly** to `POSTED`. No draft unless a later product decision requires review. |
| F3 approvals | **No separate `finances.approve`** unless a later gate proves it is needed. |
| F3 permissions | `finances.view` + `finances.manage` are sufficient. Reverse via `finances.manage`. |
| Optional later | `finances.reverse` as a distinct permission; approval thresholds; pending-approval state from the PRD. Not F3-required. |

Small organizations post directly. The PRD's `Draft → Pending Approval → Posted → Corrected/Reversed` remains a future-compatible superset. F3 implements `DRAFT? → POSTED → CORRECTED/REVERSED` and must not preclude later approval.

## 16. Correction

No destructive edit or delete of a `POSTED` event.

**Correction = linked reversal / adjustment + optional replacement.**

| Must preserve | Freeze |
|---|---|
| Actor | Who reversed / replaced |
| Reason | Required human-readable reason |
| Timestamps | `posted_at` of original; `corrected_at` / `posted_at` of correction |
| Linkage | `reversal_of_event_id` and, when used, `replacement_event_id` |

The original event remains visible as `CORRECTED` or `REVERSED`. Projections exclude reversed originals and include reversal + replacement so net activity is correct without rewriting history.

A reversal is itself a Financial Event with deterministic opposite postings. It uses a new id. It does not violate source idempotency of the original (§9).

## 17. Opening Position

Opening Position exists so organizations can start VillageClaq **without fake payments**.

### 17.1 What opening may represent

- Opening cash / account balances
- Opening arrears / receivables
- Opening member credits
- Opening liabilities (including Njangi-style member-held savings if in scope)
- Fund beginning positions

Opening arrears are **not** confirmed collections. They must not create SoA income and must not appear as payments in the contribution ledger.

### 17.2 Modes (from the PRD; F2 does not shrink them)

| Mode | Meaning |
|---|---|
| **Clean Start** | VillageClaq becomes authoritative on an explicit cutover date. No fake historical payments. |
| **Opening Position** | Current financial position is brought in without pretending VillageClaq recorded the history. |
| **Full Historical Migration** | Legacy transactions imported with immutable provenance, distinguishable from native activity. |

### 17.3 Conceptual pipeline (for later F7 / F8)

`staging → validation → approval → posting`

F3 may accept **manual Opening / Adjustment events** as a foundation. Full cutover upload, CSV/PDF importers, activation lock, and batch provenance are F7/F8 — not F3.

Opening records retain source, approver (when approved), cutover date, group, epoch, currency, and provenance. Opening balances must not appear as if they became due in the first VillageClaq reporting period.

## 18. Reports

All organization reports **project from canonical postings** (+ dimensions). They never become a second money truth.

Contribution ledger / member statement / AR aging **may join source links** to the dues subledger.

### 18.1 Invariants (frozen)

| Invariant | Rule |
|---|---|
| Account closing | `closing = opening + in − out ± transfers` |
| Transfers | Excluded from Statement of Activity |
| Loan principal | Excluded from income and expense |
| Contribution collection | Recognized once |
| Exports | Match UI totals |
| No independent money truth | No dashboard, export, or SQL shortcut that totals `payments.amount` / `amount_paid` as organization income beside the ledger |

### 18.2 Organization report catalog (projection sources)

| Report | Projects from | Must not use as truth |
|---|---|---|
| Financial Health | Postings + subledger AR/credits via source-consistent projections | Ad-hoc payment sums |
| Statement of Activity | Income/expense postings by `occurred_at` | Transfers; obligation creation; loan principal |
| Cash Movement | Custody postings: opening + cash in − cash out | Accrual/AR |
| Transaction Register / Cashbook | Posted events + postings | Drafts as activity |
| Account Balance | Derived account postings | Editable totals |
| Income / Expense reports | Classified postings + dimensions | Category-as-account confusion |
| Fund Report | Fund-dimensioned postings | Bank balance as fund balance |
| Contribution Ledger / member statement | Dues subledger joined through source links | Treating all Money In as dues |
| Parent / HQ | Per-branch native buckets | FX-netted grand total |

Every later report still needs a Report Coverage Matrix row (PRD §13.1). F6 owns catalog completion. F3 ships only foundational projections (§24).

### 18.3 Event → projection matrix (minimum freeze)

| Event | Account balance | Cash movement | SoA | Contribution / standing | Notes |
|---|---|---|---|---|---|
| Confirmed contribution collection | Yes | Yes | Income | Yes (via source link + subledger) | Obligation create: no |
| Donation / grant / other income | Yes | Yes | Income | No | Not a member due |
| Operating / venue / project / relief expense | Yes | Yes | Expense | No | |
| Reimbursement | Yes | Yes | Expense (or receivable reduce) | No | |
| Internal transfer | Yes (both accounts) | Net zero at org cash if both are cash-like; register shows both legs | **No** | No | |
| Loan disbursement | Yes | Cash down | **No** (not expense) | No | Receivable up |
| Loan principal repayment | Yes | Cash up | **No** (not income) | No | Receivable down |
| Loan interest | Yes | Yes | Income | No | |
| Opening cash | Yes | Opening, not period in/out | **No** as period activity | No | |
| Opening arrears | No org cash | No | **No** | Subledger AR / standing input | Not a payment |
| Correction / reversal | Inverse of original | Inverse of original | Inverse of original | Inverse if original touched them | Linked, not destructive |

## 19. Standing

**Do not redesign standing.**

Standing continues to use `calculateStanding()` / `useMemberStanding()` and the four existing rules (dues, attendance, relief, disputes).

**Frozen consumption rule:** Standing **MUST** consume **one canonical confirmed-dues projection** — the same contract as `money.ts` / applications.

| Forbidden | Why |
|---|---|
| SQL-vs-TS divergence | Production integrity incident class. One contract, both sides. |
| Standing reading raw `amount_paid` as a second truth after F4 | `amount_paid` becomes a projection only (§23). |
| Standing treating Opening arrears as payments | Opening arrears are inherited position, not collections. |
| Standing treating donations, expenses, transfers, loans as dues | Wrong source module. |

F3 does not change standing. F4 must wire confirmed collection events so the canonical dues projection and standing stay aligned.

| HQ / parent | Parent view of currency buckets | No cross-ledger mutate |

| Decision | Freeze |
|---|---|

## 21. Security notes

| Control | Freeze |
|---|---|
| Org / group isolation | Every financial row is group-scoped. RLS must prevent cross-group read/write. |
| Active membership | Mutation requires an **active** membership (or equivalent active authorization) in that group. |
| Append-only posted meaning | No UPDATE/DELETE of posted economic meaning. Corrections insert linked events. |
| Source idempotency | Unique source key at the database/command boundary. |
| Account / fund scoped | Events cannot post to another group's accounts or funds. |
| No cross-currency leakage | Constraints reject mixed-currency events, mixed-currency transfers, and incompatible totals. |
| No tenant bypass | Service-role / SECURITY DEFINER paths, if any, must still enforce group scope. Do not put SECURITY DEFINER in an exposed schema. |
| F0 test-tenant classification | **Migration gate only.** **NOT** a runtime financial-integrity bypass. Production request paths never skip balance, currency, idempotency, or RLS because a tenant is marked internal/test. |

## 24. F3 minimum scope

F3 implements the **foundation** in an isolated environment and proves invariants before UI expansion.

| In scope for F3 | Meaning |
|---|---|

| Accounts | Custody accounts, lifecycle, derived balances |
| Fund / category primitives | Default fund; flat categories; archive |
| Server posting command | Authoritative write path that emits balanced postings |
| Source idempotency | Unique source key + `request_id` |
| Correction / reversal foundation | Linked reversal + optional replacement |
| Manual Money In / Money Out / Transfer | Treasurer UX; same-currency transfer only |
| Foundational projections | Account balances, cashbook / register, SoA-lite |
| Tiny validation bridge | Optional narrow hook so F3 can be proven against a fixture or one safe path |

Full dues integration is **F4**, not F3.

F3 must prove: balanced postings; no transfer in SoA; one currency per event; derived balances; idempotent retries; corrections do not destroy history.

## 27. North-star scenario (design proof)

Walk **Branch A (USD)** and **Branch B (XAF)** through the following. The scenario is the acceptance story F3–F6 must remain able to satisfy. F3 proves the foundation (opening cash, donation, expense, reimbursement, transfer, SoA-lite, buckets). F4/F5 complete contribution, loan, relief, and project legs.

Parent / HQ shows **separate currency buckets**. There is no USD+XAF net.

### 27.1 Branch A — USD opening

| Step | Action | Ledger | Subledger | Forbidden outcome |
|---|---|---|---|---|
| A0 | Opening cash: Bank $20,000; Cash $500 | Opening Position events; accounts derived | — | Fake payments; SoA income |
| A1 | Opening arrears $3,000 | No org income; no cash | Dues AR $3,000 | Fake collections; standing as if paid |
| A2 | Confirmed contribution $2,000 to Bank | Money In: Bank +2000; income +2000 | AR reduces by 2000 | Second income from `amount_paid` |
| A3 | Donation $1,000 to Bank | Money In: Bank +1000; donation income | Not a due | Counted as contribution |
| A4 | Venue expense $500 from Bank | Money Out: Bank −500; expense +500 | — | Fake contribution to “account for” expense |
| A5 | Reimburse officer $100 from Cash | Money Out: Cash −100; reimbursement expense | — | Income; missing expense |
| A6 | Transfer $300 Bank → Cash | Bank −300; Cash +300 | — | SoA income or expense |
| A7 | Loan disbursement $1,000 from Bank | Bank −1000; receivable +1000 | Loan subledger | Operating expense |
| A8 | Principal repayment $200 to Bank | Bank +200; receivable −200 | Loan subledger | Income |
| A9 | Relief payout $400 from Bank | Bank −400; relief/benefit expense | Relief subledger | Missing org expense; double record |
| A10 | Project expense $250 from Bank | Bank −250; project expense (project dimension) | Project subledger | Hidden from org SoA |

### 27.2 Branch B — XAF (isolation)

Branch B records its own opening cash, a collection, and an expense in **XAF**. Nothing in Branch A’s USD ledger is converted, relabeled, or netted into Branch B. Parent view shows a USD bucket and an XAF bucket.
