## 1. Purpose

VillageClaq Financials will become the authoritative financial operating system for community organizations.

An authorized officer records a legitimate **Financial Event** once. VillageClaq then maintains the affected balances, member positions, reports, exports, standing dependencies, audit evidence, and financial-health views from that single write.

Operating promise (unchanged from the PRD):

> **Record the financial event once. VillageClaq maintains the truth everywhere else.**

Report doctrine (unchanged from the PRD):

> **A report is a view of financial truth. A report is not financial truth.**

F2 freezes the objects, ledger semantics, cash-basis rule, event taxonomy, subledger classifications, posting invariants, idempotency, accounts/funds/categories, multi-currency, dates, status, correction, opening position, report projections, standing consumption, permissions, security, Record Transaction UX, and the bounded F3 ticket cut. F3 may implement only the minimum scope in §24.

## 2. Alignment with PRD layers A–E

This design does not replace the PRD architecture. It names the canonical objects that realize each layer.

| PRD layer | Business question | Canonical realization (F2 freeze) |
|---|---|---|
| **A — Organization financial ledger** | What happened to the organization's money? | **Financial Event** is the user-understood write unit. **Postings** are the balanced accounting lines generated by that event. |
| **B — Financial accounts** | Where is the organization's money? | **Account** = custody. Balance is derived from custody postings. |
| **C — Financial dimensions** | Why did this happen and what is it for? | **Fund** (purpose/restriction), **Category** (income/expense class), optional **project/program**, optional **member**, optional **contribution type**, plus source link. Account and fund are independent dimensions. |
| **D — Specialized subledgers** | What does this module mean for members/programs? | Dues, fines, loans, projects, relief, Njangi retain their own rules. Each economic effect emits **at most one** canonical Financial Event. |
| **E — Reporting projections** | What should officers see? | All organization reports project from **all committed postings** (+ dimensions). Contribution ledger / member statement may join source links to the dues subledger. Reconciliation means compatible derivation from the same economic truth — not every report showing the same number. |

No layer may become a second money truth.

## 3. Object model

Users never see a separate Transaction object distinct from Financial Event. **Financial Event is the unit.**

### 3.1 Canonical objects

| Object | User-visible? | Meaning | Authority |
|---|---|---|---|
| **Financial Event** | Yes | The user-understood business event. Canonical write unit for the organization ledger. | One event is the single recorded fact officers and auditors talk about. |
| **Posting** | No | Balanced accounting lines generated by an event. Backend only. | Users never see debit/credit language. |
| **Account** | Yes | Custody / where money is held. | Bank, cash, mobile money, wallet, other. |
| **Fund** | Yes | Purpose / restriction. | Unrestricted/general, emergency, project, relief, other. Custody ≠ purpose. |
| **Category** | Yes | Income/expense classification. | Separate from accounts, funds, projects, and contribution types. |
| **Source link** | Audit/drilldown | Pointer to the originating financial occurrence. | `source_module` + `source_record_id` + `effect_kind` + `ledger_epoch` + `group_id`. |

Do **not** introduce a separate user-facing Transaction object unless a later gate proves it is required. F3 must not add one.

### 3.2 Dimensions on an event

Every Financial Event is scoped to the organization ledger and may carry:

| Dimension | Required? | Notes |
|---|---|---|
| Group / branch | Required | Ledger scope. Matches PRD: `group` is the authoritative financial ledger scope. |
| Ledger epoch | Required (inherited) | Group has one active currency per dated ledger epoch. Bound to the occurrence; a retry must not re-resolve against a later active epoch. |
| Currency | Required | Inherited from account + epoch. One event = one currency. |
| Account(s) | Required for money movement | Custody involved. Transfers use two accounts of the same currency. |
| Fund | Required on money events | Defaultable to unrestricted/general. F3 ordinary manual events: **one fund per event**. |
| Category | Required on Money In / Money Out | Not required on Transfer. |
| Member | Optional | Present when the event is about a person (collection, reimbursement, credit application). |
| Project / program | Optional | Dimension first. Optional dedicated project fund later if restriction requires it. |
| Contribution type | Optional | Subledger dimension; does not replace Category. |
| Source link | Required when originated by a module | Manual events use a stable manual request identity (§9). |

### 3.3 Conceptual identity (not a migration)

F3 will persist these as group-scoped rows. This section is a design contract, not DDL.

**Financial Event (conceptual fields)**

- `id`
- `group_id`
- `ledger_epoch_id` (or equivalent epoch binding)
- `currency`
- `ux_class` — `MONEY_IN` \| `MONEY_OUT` \| `TRANSFER` \| `OPENING_ADJUSTMENT`
- `category_id` (null on Transfer)
- `fund_id` (default unrestricted/general)
- `account_id` (primary custody; Transfer also has `destination_account_id`)
- `amount` (unsigned magnitude in native currency; direction comes from `ux_class` + postings)
- `member_id` (optional)
- `project_id` (optional)
- `contribution_type_id` (optional)
- `source_module`, `source_record_id`, `effect_kind` (P1-B tuple components)
- `request_id` / `correlation_id`
- `occurred_at` (effective / activity date)
- `posted_at`
- `created_at`
- `status` — `DRAFT` \| `POSTED` \| `CORRECTED` \| `REVERSED`
- `corrected_at`, `reversal_of_event_id`, `replacement_event_id` (when applicable)
- actor, reason, evidence refs

**Posting (conceptual fields)**

- `id`
- `event_id`
- `group_id`
- `account_id` (custody line **or** system/control account for income, expense, opening-position, receivable, liability — see §4)
- `fund_id`
- `amount_signed` using the debit-positive internal convention (§4.3)
- `currency`
- `occurred_at` (copied from event; reports use this)

Posting language is internal. UX copy is Money In / Money Out / Transfer / Opening-Adjustment only.

## 4. Ledger model

**Frozen choice: B — lightweight balanced posting journal behind simple UX.**

- Financial Events create balanced postings **per currency**, within the group/org ledger scope.
- Users see **Money In / Money Out / Transfer / Opening-Adjustment**.
- Users never see debit, credit, journal, chart of accounts, or trial-balance jargon.
- This is **not** QuickBooks or NetSuite.
- Do not build an enterprise chart-of-accounts builder (PRD non-goal).

### 4.1 Balance rule

For each Financial Event, generated postings must balance to **exactly zero** in that event's single native currency inside that group ledger.

**Internal convention is debit-positive.** Asset and expense increases are positive. Income, liability, and opening-position-control increases are negative. The UI never shows debit or credit.

| UX | Example | Internal debit-positive postings (never shown) |
|---|---|---|
| Money In | $100 donation to Cash | Cash **+100**; Income **−100** |
| Money Out | $50 venue / fuel from Cash | Expense **+50**; Cash **−50** |
| Transfer | $500 Bank → Cash | Bank **−500**; Cash **+500**; **no income or expense** |
| Opening | Opening cash $20,000 | Custody **+20,000**; Opening-position control **−20,000**; **not** a payment and **not** period income |

Internal control accounts (income, expense, opening position, receivable, liability) exist so postings can balance. They are not user-facing Account kinds. User-facing Accounts are custody only (§10).

### 4.2 What the journal is not

- Not accrual-basis organization books.
- Not a full double-entry teaching surface.
- Not a second write path beside subledgers.
- Not an FX engine.
- Not a dues accounts-receivable journal (§5.2).

### 4.3 Posting invariants (explicit)

A `POSTED` Financial Event is valid only when **all** of the following hold. Failure of any invariant is an atomic abort: **no partial survival**.

| Invariant | Freeze |
|---|---|
| Complete set | The event has a **complete, non-empty** posting set. |
| Exact balance | Signed postings sum to **exactly zero** in the event's native currency. |
| Shared scope | All postings share the event's `group_id`, `ledger_epoch`, `currency`, and effective date (`occurred_at`) as required. |
| Compatible scopes | Account, fund, member, and project scopes are compatible with the event group. No cross-group account or fund. |
| Custody currency | Every custody account's currency matches the event currency. |
| Exact monetary precision | Amounts use the currency's exact minor-unit precision. No float rounding. XAF/XOF are integer. |
| No partial survival | Create-event + create-postings is one transaction. A failed command leaves **zero** posted rows. |
| Posted dimensions immutable | After `POSTED`, economic dimensions (amount, currency, accounts, funds, category, member, project, dates, source key) are not rewritten. Correction is a new linked event (§16). |
| Reversal exact negate | A reversal posting set is the **exact negation** of the original posted set (same accounts, funds, currency, opposite signs, same magnitudes). |
| Projection inclusion | Projections include **original + reversal + optional replacement**. Status `CORRECTED` / `REVERSED` is presentation/history, **not** arithmetic exclusion. |

Illustrative debit-positive set that balances:

- Donation: `Cash +100`, `Income −100`
- Venue: `Expense +50`, `Cash −50`
- Transfer: `Bank −500`, `Cash +500`

### 4.4 Loan / liability primitives (journal capability only)

**F3 does not implement loans or Njangi.** The F3 journal **must** be able to post asset/receivable and liability movements **without** operating income or expense. That capability is frozen so F5 can emit classified events later.

| Later business effect | Internal debit-positive example | SoA |
|---|---|---|
| Loan disbursement | Receivable **+1,000**; Bank **−1,000** | Not expense. Not income. |
| Loan principal repayment | Bank **+200**; Receivable **−200** | Not income. Not expense. |
| Loan interest received | Bank **+50**; Income **−50** | Income only for the interest component. |
| Njangi / savings contribution | Bank **+100**; Member-liability **−100** | **Not** association income. |
| Njangi / savings payout | Member-liability **+100**; Bank **−100** | **Not** expense unless a separately classified fee/interest exists. |

Loan principal never becomes income or expense. Njangi / member savings never becomes association unrestricted income. These examples are fixtures for F3 journal capability and F3-T12 — not product features.

## 5. Cash vs accrual

**Frozen choice: A — cash-basis Statement of Activity + separate receivable/dues subledger.**

| Rule | Freeze |
|---|---|
| Creating a dues obligation | Does **not** create organization income. Does **not** create a journal AR posting. |
| Confirmed collection | Creates organization income **and** cash/account movement **once**, for the **confirmed cash amount**. Obligation application lives in the dues subledger. |
| Dues advance / unapplied dues credit | Confirmed cash over obligation is still **income once** at confirmation, plus an **allocation credit**. Later application does **not** recognize more income. |
| Refundable member money / deposit / savings | Cash increases and a member liability increases. **No** income. Refund decreases both. Never silently convert to dues income. |
| Recognition gate (P1-C) | Only server-enumerated confirmed statuses/effects may emit cash-basis SoA income. `pending` / `rejected` / `voided` / relief-misapplied never do. |
| Statement of Activity | Reads **ledger postings** only (including original + reversal + replacement). |
| Member statements / AR / aging / who-hasn't-paid | Read the **dues subledger** (and source links). Outstanding obligations and credits are reported **separately**. One member's credit never hides another's debt. |
| Double counting | Forbidden. The same economic cash collection must not appear as income in SoA from both a subledger total and a ledger posting. |

### 5.1 Avoid-double-count contract

- SoA income/expense = posted ledger lines classified as income or expense.
- Transfers never enter SoA.
- Loan principal never enters SoA as income or expense.
- Opening arrears are subledger/opening position, not period income and not fake payments.
- Contribution collection is recognized **once**, when confirmed, via the canonical event, for the confirmed cash amount.
- Applying a previously recognized dues allocation credit does **not** emit a second income event.

### 5.2 Dues receivable boundary

**Dues AR stays in the dues subledger.** F3 must **not** create a duplicate journal accounts-receivable for ordinary dues.

| Position | Where it lives | Journal effect in F3 |
|---|---|---|
| Dues obligation / opening arrears / aging | Dues subledger (F4 / F7) | **None.** No journal AR line. |
| Confirmed dues collection | Canonical Money In event | Cash + income (debit-positive: custody +, income −) |
| Unapplied confirmed dues advance | Dues allocation-credit in subledger | Already included in the collection event's income. No second event. |
| Loan receivable | Organization journal **asset** (cash was lent) | Receivable + cash − on disburse. **Different object** from dues AR. |
| Health / standing later | Consumes the **canonical dues-position** (§19) | Does not invent a second AR journal. |

Health later consumes canonical dues-position separately from journal cash and from loan receivables.

### 5.3 Member credit recognition (three kinds)

These must never be silently converted into each other.

#### 1) Dues advance / unapplied dues credit

Confirmed dues cash that exceeds currently applied obligations.

Example: member pays **$120** confirmed; current obligations **$100**.

| Effect | Amount |
|---|---|
| Cash / custody | **+120** |
| Dues income recognized **once** | **120** (internal: Income **−120**) |
| Applied to obligations | **100** |
| Unapplied allocation credit | **20** |

Applying the $20 later is **allocation only**. It does **not** recognize more income. It does **not** create a second Financial Event with SoA income.

**F4 ordinary-dues freeze:** unapplied confirmed dues advance = **already-recognized income + allocation credit**.

#### 2) Refundable member money / deposit / savings (including Njangi)

| Direction | Journal | SoA |
|---|---|---|
| Receive | Cash **+**; Member-liability **−** (liability increase) | **No income** |
| Refund / payout | Cash **−**; Member-liability **+** (liability decrease) | **No expense** unless a true fee/interest is separately classified |

Never silently convert refundable / Njangi money into dues income.

#### 3) Opening credit

Preserve the **original classification**.

- Opening **recognized dues credit** → allocation-credit. **No** current-period income. **No** fake receipt.
- Opening **refundable** credit → liability. **No** income.
- Opening arrears → dues-subledger position only. **No** income. **No** fake collection.

## 6. Event taxonomy

### 6.1 UX top-level classes (sparse)

Keep types sparse. Use category / fund / project dimensions instead of dozens of event types.

| UX class | Meaning | SoA effect | Cash/account effect |
|---|---|---|---|
| **MONEY IN** | Organization received money | Income (except when classification says otherwise — see §7 loan principal / refundable liability) | Increase custody account |
| **MONEY OUT** | Organization paid money | Expense (except when classification says otherwise — see §7 loan disbursement / liability payout) | Decrease custody account |
| **TRANSFER** | Internal movement between organization-owned accounts **and/or** fund reallocation | **Never** income or expense | See §11.2: **account transfer** vs **fund reallocation** |
| **OPENING / ADJUSTMENT** | Opening position, correction counterpart, authorized non-cash adjustment | Not ordinary period activity; see §16–§17 | As specified by the opening/adjustment postings |

### 6.2 Sparse subtypes via dimensions, not new classes

Donation, grant, sponsorship, fundraising, project income, fine collected, interest, other income are **categories** (and optional fund/project), not new UX classes.

Operating expense, reimbursement, project expense, relief payout, refund, fee, approved purchase are **categories** (and optional fund/project), not new UX classes.

Loan disbursement and loan principal repayment use Money Out / Money In **UX** with **non-operating economic classification** (§7). The UX class stays sparse; reports must honor classification, not the UX label alone.

A **real later refund** of previously recognized income is a **new economic event**, not an accounting-error correction. It normally **reverses the original income classification**. It does **not** automatically become an expense (internal: Income **+** / Cash **−**, not Expense **+** / Cash **−**).

F3 may store a backend `economic_class` on the event or infer it from category + source_module. Either is acceptable if projections stay deterministic. Do not explode UX types.

### 6.3 Record Transaction UX (frozen)

Officers record a Financial Event. They never see debit, credit, or a raw journal.

**Always shown**

- Action (Money In / Money Out / Transfer / Opening-Adjustment when that mode is offered)
- Amount + currency
- Effective date
- Custody account
- Category for ordinary Money In / Money Out
- Description for expense

**Conditional**

- Destination account (Transfer)
- Fund (when not the default, or when the officer changes it)
- Project
- Member / payer / payee
- Receipt
- Reference

**Auto-default**

- Group (current)
- Ledger epoch (current; bound to the occurrence)
- Account currency
- Effective date = today
- General / unrestricted Fund
- Last valid custody account

**Advanced / audit (not on the ordinary path)**

- Opening provenance
- Correction lineage
- Source identity (`source_module`, `source_record_id`, `effect_kind`, epoch)
- Actor / reason / timestamps

**Confirm before posting:** custody account + fund must be visible and confirmed.

Never debit/credit copy. Never an arbitrary posting builder in F3.

## 7. Subledger economic classifications (frozen)

These classifications are frozen. F4/F5 implementations must emit events that produce exactly these economic effects. They must not invent a second SoA meaning.

| Subledger business effect | Organization ledger effect | Not allowed |
|---|---|---|
| **Contribution confirmed collection** | Income + asset (cash/account) increase, for the **confirmed cash amount**, **once** | Treating obligation creation as income; counting collection twice; treating later credit application as new income |
| **Dues remaining / AR** | Subledger AR only | SoA income; **duplicate journal AR** |
| **Dues advance / unapplied allocation credit** | Already-recognized income from the collection event + subledger allocation credit | Second income when the credit is later applied; converting into refundable liability |
| **Fine assessment** | Non-cash receivable / subledger | Organization income at assessment |
| **Fine payment** | Income (or fine-income category) + cash | Ignoring cash; posting income at assessment and again at payment |
| **Loan disbursement** | Asset reclass / receivable increase + cash decrease | Operating expense |
| **Loan principal repayment** | Cash increase + receivable decrease | Income |
| **Loan interest payment** | Income + cash | Treating interest as principal |
| **Relief contribution** | Income (or restricted fund income) + cash | Unrestricted income if the fund is restricted |
| **Relief payout** | Expense (or benefit expense) + cash | Omitting org-ledger expense while paying cash |
| **Relief remittance** | As already designed for remittance, without double counting | Posting the same cash as both income and remittance income |
| **Project contribution** | Income (often restricted / project fund) + cash | Treating it as unrestricted operating income when restricted |
| **Project expense** | Expense + cash | Hiding it from org SoA |
| **Njangi contribution / savings** | Liability to members (or member-held savings) + cash | Association unrestricted income |
| **Njangi payout** | Liability decrease + cash | Expense (unless a true fee/interest component is separately classified) |
| **Reimbursement** | Expense (or reduce prior receivable) + cash | Fake contribution; double expense |
| **Refundable member money / deposit** | Liability + cash; refund reverses both | Invented income; silent conversion to dues credit |
| **Opening recognized dues credit** | Allocation-credit only | Current-period income; fake receipt |
| **Opening refundable credit** | Liability | Current-period income |
| **Member credit application (dues allocation)** | Reduces AR / applies allocation; **no new income** | Creating income a second time |
| **Internal transfer** | Asset ↔ asset and/or fund reallocation; never income/expense | Income or expense |
| **Accounting-error correction** | Original + exact reversal + optional replacement, all retained | Excluding the original from arithmetic; treating a later economic refund as a silent rewrite |

Remittance, credits, and allocations must preserve the invariant in §8: one business effect, one canonical event, no double posting.

## 8. Subledger → ledger invariant

**ONE subledger business effect → AT MOST ONE canonical Financial Event → deterministic Postings → all organization reports derive from those postings.**

| Rule | Freeze |
|---|---|
| Cardinality | One confirmed economic effect creates at most one Financial Event. |
| Determinism | The same source occurrence + effect always yields the same posting set. |
| Report source | Org reports (SoA, Cashbook, Cash Movement, account balances, fund reports) read **all committed postings**. |
| Subledger remains specialized | Obligation allocation, arrears, credit **classification**, standing inputs, loan schedules, Njangi rotations stay in the module. |
| Double posting | Prevented by source idempotency (§9). |
| Preferred integration style | **A: subledger generates canonical events.** Do not rewrite modules as ledger-first. |

A module may decide that a business action has **no** organization-ledger effect (example: creating a dues obligation). That is zero events, which satisfies “at most one.”

A module must not write organization cash/income/expense totals by any path other than the canonical event.

## 9. Idempotency

Retries, crons, webhooks, imports, and client double-submits must not double-post.

**Natural key (mandatory, P1-B):**

`(group_id, source_module, source_record_id, effect_kind, ledger_epoch)`

`group_id` is part of the tuple. It is not an informal “plus scope.”

| # | Rule | Freeze |
|---|---|---|
| 1 | `source_record_id` | Immutable **financial occurrence** identity: a receipt, repayment, disbursement, or posting command. **Not** a member id, aggregate loan id, import-job id alone, or mutable parent. |
| 2 | `effect_kind` | **Server-enumerated** (examples: `principal`, `interest`, `fee`, `collection`, `reversal`, `replacement`, `opening_custody`). Not arbitrary retry text. |
| 3 | Epoch binding | Epoch is bound to the **occurrence**. A retry must **not** re-resolve against a later active epoch. |
| 4 | Identical key + identical payload | Return the **original** event. Do not create a second event. |
| 5 | Identical key + **different** payload | **CONFLICT / FAIL.** Payload includes amount, currency, `occurred_at`, account, fund, category, member, project, destination, and economic class. |
| 6 | Manual request identity | Stable across retries (`request_id` / manual `source_record_id`). The same officer retry must collide on the same key. |
| 7 | Correction identity | Correction commands have their **own** stable identity. **At most one reversal** per target event. Further corrections target the **replacement**, not a second reversal of the original. |
| 8 | Import / cutover | Cannot repost the same occurrence by changing batch id or epoch. Occurrence identity survives the import job. |
| 9 | Authorization on replay | Authorization is **revalidated** on replay **before** returning the existing event. A now-unauthorized caller does not receive a successful replay. |
| 10 | Concurrency lock | Lock is taken **before** event creation. Do **not** rely only on `SELECT FOR UPDATE` of a row that does not exist yet. Use an **advisory lock** or **claim-row lock**, **plus** the unique constraint. |

| Mechanism | Freeze |
|---|---|
| Unique constraint | `UNIQUE (group_id, source_module, source_record_id, effect_kind, ledger_epoch)` |
| Pre-insert lock | Advisory lock or claim-row keyed by that tuple, acquired before insert. |
| Client retries | `request_id` (or equivalent) on the posting command; maps to a stable manual occurrence. |
| Correction | New event, new source occurrence, linked to the original. Does not reuse the original tuple as a second primary post. |

F3 posting command must enforce this at the authoritative server boundary, not only in the UI. **Never ship a non-idempotent posting path.**

## 10. Accounts

**Account = custody. Where money is held.**

| Decision | Freeze |
|---|---|
| Kinds | `bank`, `cash`, `mobile_money`, `wallet`, `other` |
| Currency | **Single-currency per account** |
| Balance | **Derived from custody postings for that account.** No manually editable authoritative totals. |
| Scope | Group-scoped (branch ledger). |
| Opening | Via **Opening Position** events only. |
| Lifecycle | `active` → `inactive` → `closed` |
| Currency after open | **Immutable.** To change currency: close the account and open a new one. |
| Epoch | Account belongs to the group's ledger epoch / currency rules. |

### 10.1 What officers cannot do

- Type over a balance field and make that the truth.
- Mix currencies in one account.
- Transfer across currencies in F3 (ordinary transfer is **same-currency only**).
- Use an account as a category, fund, or project.

### 10.2 Derived account balance

**ACCOUNT BALANCE** = sum of **custody postings** for that account (all committed postings, including original + reversal + replacement).

Opening is itself posting-backed. There is no side table of authoritative running totals.

Do not define account balance as “sum of every signed posting on the event” in a way that collapses a balanced event to zero and then treats that as the account. Account balance reads **custody lines for that account only**.

## 11. Funds

**ACCOUNT = where. FUND = purpose.**

Account and fund are **independent dimensions**.

- One account may hold several funds.
- One fund may live in several accounts.
- Ordinary transfers **normally preserve fund**.
- Restricted money in the same custody account is **fund attribution**, not a second cash pile.

### 11.1 Three fund / cash measures

Do **not** define “fund balance” as the sum of every signed posting. A balanced event sums to zero; that definition is meaningless.

| Measure | Definition | Used for |
|---|---|---|
| **ACCOUNT BALANCE** | Custody postings for one account | Where the money sits |
| **FUND CASH** | Custody postings **attributed to** that fund | Restricted vs general cash held |
| **FUND NET POSITION** | Assets attributed to the fund **minus** liabilities attributed to the fund | Purpose net of member-held / other fund liabilities |

Financial Health must not treat FUND CASH or ACCOUNT BALANCE as automatically spendable unrestricted association money (§18.4).

### 11.2 Account transfer vs fund reallocation

Both are UX class **TRANSFER**. Neither is income or expense.

| Kind | Example (debit-positive) | Meaning |
|---|---|---|
| **ACCOUNT TRANSFER** | Bank/General **−100**; Cash/General **+100** | Custody moved; fund preserved |
| **FUND REALLOCATION** | Bank/General **−100**; Bank/Relief **+100** | Same custody; purpose changed |

F3: **one fund per ordinary manual event** is acceptable. **No interfund AR/AP.** **No fund-reallocation UI in F3** unless a later acceptance proof truly requires it. The journal must still be able to represent fund-attributed custody lines.

### 11.3 Other fund decisions

| Decision | Freeze |
|---|---|
| Default fund | Unrestricted / general. Every group has one. |
| Money events | **Mandatory fund**, defaultable to unrestricted/general. |
| Scope | Org / group. |
| Split across funds on one event | Allowed later if needed. **F3 ordinary manual events: one-fund-per-event.** |
| Projects | **Simplest freeze:** project is a **dimension**. Optional dedicated project fund when restriction requires a separate purpose bucket. Do not require both for F3. |

Funds are not Accounts. Funds are not Categories. Funds are not contribution types.

## 16. Correction

No destructive edit or delete of a `POSTED` event.

**Correction = ORIGINAL + EXACT REVERSAL + OPTIONAL REPLACEMENT.**

**All committed financial postings remain in projections.** Status `CORRECTED` / `REVERSED` is presentation and history, **not** arithmetic exclusion.

### 16.1 Arithmetic (P0 — R1)

Example: original donation **+500**, exact reversal **−500**, replacement **+450**.

| Wrong | Right |
|---|---|
| Exclude original, then add reversal + replacement → **−50** | Keep original + reversal + replacement → **450** |

Projections that drop the reversed original and then apply the inverse **double-count the reversal**.

### 16.2 What must be preserved

| Must preserve | Freeze |
|---|---|
| Actor | Who reversed / replaced |
| Reason | Required human-readable reason |
| Timestamps | `posted_at` of original; `corrected_at` / `posted_at` of correction (**audit only**) |
| Linkage | `reversal_of_event_id` and, when used, `replacement_event_id` |
| Exact negate | Reversal posting set = exact negation of the original set |
| Effective dates | Inverse **may** use the original `occurred_at`; replacement uses the intended corrected date |
| Identity | Correction command has its own stable source identity (§9 rule 7). At most **one** reversal per target event. Further corrections target the replacement. |

The original event remains visible as `CORRECTED` or `REVERSED`. Its postings **remain in the committed set**.

A reversal is itself a Financial Event with deterministic opposite postings. It uses a new id and a new source occurrence. It does not violate source idempotency of the original (§9).

### 16.3 Error correction vs later economic refund

| Kind | Treatment |
|---|---|
| **Accounting-error correction** | Original + exact reversal + optional replacement. Used when the recorded fact was wrong. |
| **Real later refund** | A **new economic event**, not an error correction. Typically a Money Out that **reverses the original income classification** (Income **+** / Cash **−** in debit-positive). It does **not** automatically become an expense. |

**P1-D MVP:** `finances.manage` may correct/reverse **only** through that linked-audit path. No silent rewrite of posted rows. A distinct high-trust cutover/opening privilege may be added later (F7); it is **not** F3 and is **not** implied by `finances.manage` today.

## 17. Opening Position

### 17.1 What opening may represent

| Opening fact | Canonical treatment | F3 UI? |
|---|---|---|
| Opening bank / cash | Custody **+** vs opening-position **control −**. Not period income. Not a receipt. | **Yes — manual only** |

They must **not** appear as confirmed-collection income on SoA, must not appear as payments in the contribution ledger, and must not enter the confirmed-dues projection that standing consumes.

### 17.3 Conceptual pipeline (for later F7 / F8)

`staging → validation → approval → posting`

**F3 only:** manual opening **custody** + **fund** + **provenance**. No AR UI, no loan UI, no Njangi UI, no cutover upload UI.

Full cutover upload, CSV/PDF importers, activation lock, batch provenance, dues/loan/Njangi opening lines are F7/F8 — not F3. A later high-trust cutover/opening privilege (P1-D) may gate F7 activation; it is out of F3 MVP.

Opening records retain source, approver (when approved), cutover date, group, epoch, currency, and provenance. Opening balances must not appear as if they became due in the first VillageClaq reporting period.

Import/cutover must obey §9 rule 8: the same occurrence cannot be reposted by changing batch or epoch.

## 18. Reports

All organization reports **project from all committed canonical postings** (+ dimensions). They never become a second money truth.

Contribution ledger / member statement / AR aging **may join source links** to the dues subledger.

**Reconciliation** means reports are **compatible derivations from the same economic truth**. It does **not** mean every report shows the same number. Cash, SoA, dues AR, loan principal, and restricted fund cash answer different questions.

### 18.1 Invariants (frozen)

| Invariant | Rule |
|---|---|
| Account closing | `ACCOUNT BALANCE` from custody postings for that account, including original + reversal + replacement |
| Transfers | Excluded from Statement of Activity |
| Loan principal | Excluded from income and expense |
| Contribution collection | Recognized once, for confirmed cash |
| Dues advance application | No second income |
| Outstanding vs credit | Obligations and credits reported separately; one member's credit never nets against another's debt |
| Correction arithmetic | Include original + exact reversal + optional replacement. Do **not** exclude the reversed original. |
| Exports | Match the UI total for the **same** projection |
| No independent money truth | No dashboard, export, or SQL shortcut that totals `payments.amount` / `amount_paid` as organization income beside the ledger |

## 21. Security notes

| Control | Freeze |
|---|---|
| Org / group isolation | Every financial row is group-scoped. RLS must prevent cross-group read/write. |
| Active membership | Mutation requires an **active** membership (or equivalent active authorization) in that group. |
| Append-only posted meaning | No UPDATE/DELETE of posted economic meaning. Corrections insert linked events. |
| Source idempotency | Unique source key `(group_id, source_module, source_record_id, effect_kind, ledger_epoch)` at the database/command boundary, plus pre-insert lock. |
| Account / fund scoped | Events cannot post to another group's accounts or funds. |
| No cross-currency leakage | Constraints reject mixed-currency events, mixed-currency transfers, and incompatible totals. |
| No tenant bypass | Service-role / SECURITY DEFINER paths, if any, must still enforce group scope. Do not put SECURITY DEFINER in an exposed schema. |
| F0 test-tenant classification | **Migration gate only.** **NOT** a runtime financial-integrity bypass. Production request paths never skip balance, currency, idempotency, or RLS because a tenant is marked internal/test. |

Daybreak Blue reviews schema, RLS, and SECURITY DEFINER before F3 lands. Views that project balances must use `security_invoker` (or equivalent) so they do not bypass RLS.

These notes remain in force. **P1-A through P1-G below are mandatory before F2 PASS.** They pin the security boundary; they do not reopen Chief architectural decisions.

### 21.1 Security Design Pins (P1-A–H) — mandatory before F2 PASS

F2 does not PASS until this section is present on this named artifact. Implementers encode these pins. They do not substitute a weaker client-side check.

| Pin | Title | Frozen security contract |
|---|---|---|
| **P1-A** | Posting authority | `financial_events`, `postings`, and `account_balances` (or any derived balance materialization) are **not client-writable**. Only **SECURITY DEFINER** RPCs with `search_path = ''` may create or reverse posted financial truth. RLS is **deny-by-default** for `authenticated` writes on those objects. Direct `INSERT`/`UPDATE`/`DELETE` from the browser client, anon key, or ordinary authenticated role is forbidden. |
| **P1-B** | Idempotency key | Unique natural key **`(group_id, source_module, source_record_id, effect_kind, ledger_epoch)`** plus a **pre-insert** advisory or claim-row lock **and** the unique constraint. `source_record_id` is an immutable occurrence. `effect_kind` is server-enumerated. Epoch is bound to the occurrence. Identical key + identical payload → return original **after authorization revalidation**. Identical key + different payload → **CONFLICT**. `request_id` covers client-retry of a manual command. |
| **P1-C** | Recognition gate | The **server** enumerates which payment statuses / effect kinds may emit **cash-basis SoA income**. `pending`, `rejected`, `voided`, and **relief-misapplied** **never** post SoA income. #### P1-A — posting authority (detail)

| Object (conceptual name) | `authenticated` RLS writes | Who may mutate posted meaning |
|---|---|---|
| `financial_events` | Deny by default | SECURITY DEFINER create/reverse RPCs only (`search_path = ''`) |
| `postings` | Deny by default | Same RPCs only; never a standalone client insert |
| `account_balances` | Deny by default | Not a write API. Balance is derived from postings. If a projection table exists, only the RPC / invoker-safe job that rebuilds from postings may write it. Officers never edit a total. |

RPC rules (design, not DDL):

- `SECURITY DEFINER` + `search_path = ''` (no object-resolution hijack).
- Not placed in an exposed schema as a bypass.
- Still enforce group scope, active membership, `finances.manage` (or later cutover privilege), currency/epoch, P1-B lock, and P1-C recognition inside the function.
- F0 internal test-tenant classification remains a **migration gate only** — not a runtime skip of P1-A.

#### P1-B — natural key and lock (detail)

Required unique constraint (illustrative, not DDL):

`UNIQUE (group_id, source_module, source_record_id, effect_kind, ledger_epoch)`

Required concurrency (illustrative, not DDL):

1. Compute the tuple (epoch **from the occurrence**, not “whatever is active now” on retry).
2. Acquire **advisory lock** or insert/claim a lock row for that tuple.
3. If a row exists: **revalidate authorization**; compare payload; return original **or** CONFLICT.
4. If no row exists: create the event and its complete posting set in the same transaction.
5. Unique constraint remains the last-line race guard.

Do **not** implement this as `SELECT FOR UPDATE` on a financial_events row that does not exist yet.

`effect_kind` is a **server enum**. It is why one occurrence may legally produce at most one event per economic effect (confirmed collection vs reversal of that collection) without colliding incorrectly and without allowing two confirmed-collection posts.

Changed payload on the same key is **never** a silent reuse.

| `pending` | **Never** |
| `rejected` | **Never** |

| Relief-misapplied | **Never** |
